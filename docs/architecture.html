Architecture

A runtime built around data, time, and boundaries.

The engine is split so that rendering, simulation, scripting, and authoring can evolve independently. Nothing in the hot path depends on Blender, on a specific windowing system, or on the frame rate.

1. Layers and data flow

Dependencies point inward. The runtime never includes Blender headers; the bridge is a protocol, not a link-time dependency.

Static engine library

bge_engine contains platform, core, math, ECS, scene, renderer, asset, and script modules. A game links it and supplies its own main and content.

Thin executable

The sandbox proves the engine as a consumer would use it: create window, load content, run the scene, render, shut down. No engine logic lives in main.

2. ECS and scene graph

Entities are stable handles; components are dense arrays; hierarchies are explicit components, not pointers hidden in objects.

struct Entity { uint32_t index; uint32_t generation; };

// One sparse-set pool per component type.
template <typename T> class ComponentPool {
    std::vector<T>        dense;     // packed component data
    std::vector<uint32_t> indices;   // entity index for each dense slot
    std::vector<uint32_t> sparse;    // entity index -> dense slot
};

// Iterate the smallest matching pool, then verify the rest.
world.each<Transform, MeshRenderer>([&](Entity e, Transform& t, MeshRenderer& m) {
    queue.push(e, t.world, m);
});

Generational handles make stale references fail safely. Swap-remove keeps iteration dense. Hierarchy is represented by Parent and Children components; world matrices are recomputed from roots after local transforms change. This avoids the pointer-heavy scene graph that made BGE object access both slow and fragile.

3. Fixed timestep

The single most important behavioural fix over the original engine.

while (accumulator >= step) {
    scene.fixed_update(step);   // 1/120 s, always
    accumulator -= step;
}
float alpha = accumulator / step;
renderer.render(scene, alpha);  // interpolate visual state

Scripts, gameplay, and physics never read the render delta. A 30 FPS frame and a 240 FPS frame produce the same simulation. The accumulator is clamped after a stall so a breakpoint or window drag cannot trigger a spiral of death.

4. Job system

A fork-join pool with a main-thread participant, designed for frame-scoped parallel work.

  • parallel_for(begin, end, grain, fn) splits work into chunks and lets the calling thread execute jobs too.
  • Thread count defaults to logical cores − 1 workers, plus the main thread.
  • Workers wait on a condition variable; the pool is created once and reused.
  • Planned: work stealing, job dependencies, and a separate asset IO queue.

5. Renderer

Forward PBR today, behind an RHI boundary that can grow a Vulkan backend without touching scene code.

shadow pass ──▶ HDR scene pass ──▶ post pass ──▶ swapchain
              ├─ sky gradient/sun
              ├─ instanced opaque PBR
              └─ (future) transparent, UI, debug lines

Batching

Visible renderables sort by mesh + material, then draw with glDrawElementsInstancedBaseInstance. One instance buffer per frame.

Culling

Mesh bounds transformed to world space and tested against six frustum planes. Shadow casters are culled against the light frustum.

Shading

Cook-Torrance GGX, Smith visibility, Schlick Fresnel, sun / point / spot / area lights, environment ambient, PCF shadows, distance fog.

HDR

RGBA16F scene target, exposure, Standard (linear to sRGB) and ACES/AgX-approximation tone mapping, optional vignette and grade, FXAA in a fullscreen post pass.

Textures

stb_image decode, sRGB albedo upload, mipmaps, anisotropic filtering, Radiance .hdr environments in RGBA16F.

Future

Cascaded shadows, clustered lights, SSAO, bloom, TAA, GPU-driven culling, Vulkan RHI.

5b. Blender scene bridge

A file-based pipeline keeps Blender out of the runtime while letting real scenes drive the engine.

Blender (Python)          engine
tools/bge_export.py  ──▶  scene.bgescene  ──▶  scene_loader.cpp  ──▶  ECS + renderer
                          scene.bin (verts, indices)
                          textures/ (png, hdr)

Export

The evaluated depsgraph is walked, so modifiers, curves and text become real meshes. Transforms are baked into world space and converted from Blender's Z-up to the engine's Y-up.

Format

JSON manifest plus a packed binary buffer, parsed by the engine's own dependency-free JSON reader. No third-party runtime dependencies.

Verification

tools/parity_check.py renders the same scene in Cycles and in the engine and reports a block-by-block colour difference.

6. Physics

The target is Jolt Physics: active, deterministic, multithreaded, and well-suited to a modern character controller. Physics runs on the fixed step and writes transforms back through the ECS. Interpolation state is kept separately so rendering stays smooth.

M0 note: physics is not wired yet. The sandbox uses kinematic demo motion only. Jolt integration is the first task of M1, after the renderer and scripting host are stable.

7. Scripting

Python is a gameplay language, not the engine's implementation language.

  • CPython is embedded once per runtime; the GIL stays on the logic thread.
  • Entities are exposed as lightweight handles, not raw C++ pointers.
  • Hot paths (transforms, rendering, physics) stay native; scripts orchestrate.
  • The bge module is versioned and documented; a compatibility layer maps common 2.49b-era APIs where practical.
  • Script components declare start, update(dt), and stop entry points.
engine/src/script/python_host.cpp
  ├─ native layer  (bge._native: find, location, rotation, scale, spawn, ...)
  └─ Python layer  (bge.types, bge.objects, bge.logic.scene, bge.app.handlers)

The user facing API is written in Python on top of a thin C++ bridge, so new surface area is added without touching the engine. Today the module covers vectors, object lookup, transforms, visibility, scene spawning and per-frame handlers; controllers, logic bricks and timers come next.

The compatibility mapping is tracked in Compatibility.

8. Asset pipeline

Blender / DCC ──▶ glTF + PNG ──▶ importer ──▶ validator ──▶ cooker ──▶ pack
                                                              │
                                             runtime loads ◀─┘

Source assets are never loaded by a shipped game. The cooker resolves dependencies, converts textures, strips unused data, and emits a versioned pack. Hot reload is a development-only path that watches source files and swaps resources live.

9. Blender live link

The old workflow's magic was the absence of an export step. We preserve that with a persistent connection instead of embedding the engine inside Blender.

  1. Blender addon starts or connects to the runtime over a local socket.
  2. Scene graph, meshes, materials, and transforms are sent incrementally.
  3. Press Play in Blender: addon switches the runtime into play mode and mirrors input/state.
  4. Selecting an entity in Blender highlights it in the runtime and vice versa.
  5. Bake lighting, occlusion, and navigation data back into the cooked scene.

10. Clean-room policy

We do not copy the original BGE source. Behaviour and public API names may be studied for compatibility, but implementation is written from specifications and original code. Dependencies are vendored with their licenses recorded. This keeps the engine free to use a permissive license and avoids inheriting GPL obligations.

Third-party code currently vendored: glad (MIT), stb_image / stb_image_write (public domain / MIT). Each dependency's license is stored alongside it.
