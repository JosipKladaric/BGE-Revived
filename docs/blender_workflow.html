Authoring workflow

Make the game in Blender. Ship it from the engine.

The add-on turns Blender into the front end: export the scene, press Play to run it in the BGE Revived runtime while you keep editing, and package a self contained game folder when you are done.

Working Add-on, live link and packaging are implemented and verified

The loop

1. Author

Model, light and script your scene in Blender as usual. The add-on reads the evaluated scene, so modifiers, curves and text are included.

2. Export

Export writes scene.bgescene, a JSON manifest plus a packed binary buffer, with the textures next to it.

3. Play

Play starts the engine on that scene. Every edit you make in Blender is re-exported and reloaded in place, so the running game follows the viewport.

4. Package

Package Game assembles a folder with the runtime, the scene, the textures and the engine assets, plus an optional zip.

Installing the add-on

The add-on lives in tools/blender_addon/bge_revival/. Install it like any Blender add-on:

# 1. build an installable zip of the add-on
python tools\make_addon_zip.py      # writes build/bge_revival.zip

# 2. Blender > Preferences > Add-ons > Install from Disk... > bge_revival.zip
# 3. enable "Game: BGE Revived"

Then open the 3D View sidebar (N) and pick the BGE Revived tab. In the add-on preferences, point Engine folder at the repository root (the folder that contains tools/bge_export.py); everything else is optional.

Physics from Blender

Rigid body objects

Add a rigid body in Blender (Physics ▸ Rigid Body). Active bodies fall and tumble; passive bodies stay where they are and act as floors and walls.

What is exported

Shape (box or sphere), mass, friction, restitution and the object bounds. The body starts at the object's world transform.

What simulates

Jolt Physics 5.3.0 steps the bodies on the fixed timestep in the game runtime; the renderer interpolates the transforms.

Capsule, convex hull and mesh collision shapes are exported as an enclosing box for now, so blocks and spheres give the most predictable results.

├── game.bgescene     the exported scene
├── scene.bin         the packed vertex and index data
├── textures/         the textures the scene references
├── assets/           shaders and engine assets
├── python312.dll     the embedded interpreter (only when scripting is used)

The folder is self contained: copy it anywhere and run the executable. The runtime loads game.bgescene next to itself, so a player never needs Blender, Python or the source repository.

BGE Revived as a render engine

The add-on registers a render engine with Blender, so BGE Revived appears next to Cycles and EEVEE in the render properties. Select it, press F12, and the scene is rendered by the game engine: the same PBR shading, the same shadow map, the same tone mapping. The result is written to the output path and shown in the image editor.

Render properties  ▸  Render engine  ▸  BGE Revived     # then F12

The engine renders at Blender's render resolution and with Blender's active camera, so the F12 image is the frame the game shows. The frame is read from a named shared memory region, so the resolution is exact and the pixels are not copied through the socket.

One Blender limitation. Blender does not expose its render result buffer to Python render engines, so the F12 window itself stays empty and the add-on writes the image to the output path (and shows it in the image editor) instead.

See the real engine output while you work

The preview answers "will this look right in the game?". The engine renders the scene with its own renderer - the same PBR shading, the same shadows, the same tone mapping - and the frames come back to Blender.

Start Preview

The add-on exports the scene into a preview folder and starts the engine in preview mode: a hidden window that renders at the chosen resolution and publishes each frame into a named shared memory region.

Back in Blender

The frames are mirrored into a Blender image, shown in the image editor, and drawn over the camera frame in the 3D View (or in the corner).

Always current

Because the preview shares the live link, every edit is re-exported and re-rendered automatically. The add-on reads whatever the engine published last instead of waiting for a round trip, so the delay is one timer tick (50 ms) plus the engine's frame time.

Blender                        engine (preview mode)

  │  re-export scene.bgescene
  ├──────────────────────────▶  reload the scene
                                render 960x540
                                write frame.png
  ◀──────────────────────────┤
mirror the frame into the image editor
How the frames come back. The engine runs a small local TCP server (--preview-port) for scenes, commands and short replies. The pixels do not go through it: the engine publishes each frame into a named shared memory region and the add-on reads the newest complete frame from there, so nothing is copied over a socket. A file based transport (a watched frame.png) is kept as the fallback for setups where neither is available.

Incremental updates

A full re-export on every keystroke would be wasteful, so the live link sends only what changed. The add-on watches the objects Blender reports as updated and pushes the smallest possible update:

Change in BlenderWhat is transferred
An object was moved or rotatedA 16 float matrix and the object name
A mesh was editedOnly that mesh's vertices and indices; the engine uploads it and rebinds the object
An object was added or removedThe name, and the mesh that goes with it
A light or camera changedA full re-export (lights and cameras are cheap to re-read)
Keyframes changedThe animation is re-sampled on the next full export

The engine applies the update to the running scene: the transform is decomposed into position, rotation and scale, and a new mesh replaces the old GPU buffer in place. Nothing is rebuilt that did not change.

How the live link works

Scene updates go over a socket; frames come back through shared memory. The file watch is kept as a fallback, so the link still works across machines and cannot deadlock the editor:

  1. The add-on registers a depsgraph handler; any change to the scene marks it dirty.
  2. A timer pushes only what changed over the socket (or re-exports the whole scene when the change is not incremental).
  3. The engine applies the update to the running scene and keeps rendering.
  4. With --watch, the engine also polls the manifest's modification time every 200 ms and reloads the scene in place when it changes.

The engine publishes every rendered frame into the shared region with a seqlock, so the add-on can take the newest frame at any moment and never sees a half written one.

Scripting the exported game

A packaged game can carry a startup.py next to the scene. The runtime starts it automatically, and objects can carry controllers with their own scripts.

# startup.py
import bge

bge.app.handlers.post_update.append(update)

def update():
    knot = bge.objects.get("Knot")
    if knot:
        knot.applyRotation((0.0, 0.0, 1.0), bge._native.delta() * 0.8)

Limits

  • The live link re-exports the changed parts of the scene; transforms and edited meshes are pushed incrementally.
  • Each reload re-uploads the meshes, so the GPU resources of the previous scene are not reclaimed yet.
  • Only the active Blender scene is exported; collections and linked libraries are flattened first.
  • Armatures, shape keys and particles are not part of the export yet; object transform animation is sampled.
